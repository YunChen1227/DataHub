## 1 数据流转

1. 构造请求数据：按接口规范构造业务数据，程序内做 AES 加密；
2. 发送请求数据：POST（form-data 格式）发给上游；
3. 上游接收请求：解析、拆包、格式校验，合法则处理；
4. 返回响应数据；
5. 合作方对响应做业务处理。

前置条件：**需要先添加对应服务器白名单**。

## 2 Request 请求

### 2.1 请求方法
POST

### 2.2 请求格式
- 格式1：`Content-Type: multipart/form-data`
- 格式2：`Content-Type: application/x-www-form-urlencoded`

本服务用格式 2（`application/x-www-form-urlencoded`）。

### 2.3 请求参数（form 字段）

| 字段 | 类型 | 必传 | 含义 |
|---|---|---|---|
| `institution_id` | String | 是 | 上游给客户分配的唯一编号 |
| `biz_data` | String | 是 | 业务数据（见 2.5），需 AES 加密（见 2.4）；加密是否成功可用在线 AES 网站校验 |

### 2.4 加密过程

- **AES 分组模式 `ECB`，最后一个分组填充 `PKCS5Padding`**（在线工具中对应 PKCS7 / 128bits / UTF-8）。
- 流程：`biz_data` 明文 JSON 化 → 用上游分配的 AES 密钥加密 → 密文 **Base64** 编码 → 放入 `biz_data` 字段。
- 在线校验工具（原文推荐）：https://the-x.cn/cryptography/Aes.aspx
- **密钥编码形态必须验算**：AES 只接受 16/24/32 字节。兄弟产品 zlf 的沙箱密钥
  `Q0ymUIe1t26ZfG7s` 是 16 字节 ASCII。本服务的 `multiLoanAESKey` 依次尝试
  「原始字节 → hex 解码 → Base64 解码」，取第一个落在合法长度上的形态；全都不合法
  **立刻报错**，不把非法长度交给 `aes.NewCipher`（见 `multiloan_test.go`
  的 `TestMultiLoanAESKeyDerivation`）。长度恰为 16/24/32 的串一律按原始字节采用。

### 2.5 业务数据内容（biz_data 明文 JSON）

**七个字段上游全部标「必传」，一个都不能少。** 字段名逐字照抄（`ident_number`
是下划线、`licenseUrl`/`licenseType` 是小驼峰——上游原样混用，不许"纠正"）。

| 字段 | 类型 | 必传 | 含义 |
|---|---|---|---|
| `name` | String | 是 | 姓名 |
| `ident_number` | String | 是 | 身份证号 |
| `phone` | String | 是 | 手机号 |
| `service` | String | 是 | 接口名称，默认值 `"financial_rent_service"` |
| `mode` | String | 是 | 接口模式，`"mode_loan_intent_v1"` |
| `licenseUrl` | String | 是 | 授权书 OSS 地址（需先上传到布尔提供的 OSS），支持 pdf/jpg/jpeg/png/bmp。样例：`https://shouwei.oss-cn-shanghai.aliyuncs.com/approve_files/XXX.pdf` |
| `licenseType` | Integer | 是 | 文件类型，`0`: jpg/jpeg/png/bmp；`1`: pdf |

biz_data 明文模板（原文；示例是脱敏的，实际使用需真实数据）：

```json
{
  "name": "xx",
  "ident_number": "xx",
  "phone": "xx",
  "service": "financial_rent_service",
  "mode": "mode_loan_intent_v1",
  "licenseUrl": "授权书oss地址",
  "licenseType": 0
}
```

**网关入参口径**：`name` + `idCard` + `mobile` 三要素**均必填**，由
`parse.ParseWithName` 前置拦截（对外手册承诺"参数非法不调用上游、不计费"）。
`service`/`mode`/`licenseUrl`/`licenseType` 是我方配置侧的固定值，不来自下游入参。

## 3 Response 响应

### 3.1 响应格式
JSON 返回：`Accept: application/json;charset=utf-8`

### 3.2 响应字段

#### 3.2.1 外层字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `resp_code` | String | 响应状态码（见 §4） |
| `resp_data` | String | 响应的主体数据 |
| `resp_msg` | String | 响应状态码对应的文字描述 |
| `resp_order` | String | **响应订单号**（唯一上游标识，对账用） |
| `timestamp` | String | 时间戳 |

> **文档自相矛盾**：§3.2.1 把 `resp_data` 的类型标成 `String`，而 §3.2.3 的成功示例里
> 它是一个 JSON **对象**。本服务**两种都兼容**（`normalizeMultiLoanData`：是 JSON
> 字符串时先解一层引号再压缩，是对象时直接压缩），不挑一个赌。

#### 3.2.2 响应主体数据（`resp_data`）

约 **700 个**字段，分两类：

1. **决策类 `Rule_*`**
   | 字段 | 含义 |
   |---|---|
   | `Rule_final_decision` | 最终决策结果：`Accept` 通过 / `Reject` 拒绝 / `Review` 复议 |
   | `Rule_final_weight` | 最终规则评分 |
   | `Rule_name_QJF0xx` | 命中规则的名称（如 `QJF045` = 「在非银机构多次申请-低度」、`QJF076` 在非银机构申请次数极多、`QJF077` 在非银机构申请次数较多、`QJF078` 在银行机构申请次数极多、`QJF079` 在银行机构申请次数较多） |
   | `Rule_weight_QJF0xx` | 对应规则的权重 |

2. **多头借贷因子类 `als_*`**（全部 String 类型）字段名按固定构词法拼装：

   `als_<时间窗>_<主体>_<机构/业务类别>_<度量>`

   | 片段 | 取值 | 含义 |
   |---|---|---|
   | 时间窗 | `d7` / `d15` / `m1` / `m3` / `m6` / `m12` | 近 7 天 / 15 天 / 1、3、6、12 个月 |
   | | `fst` / `lst` | 距最早 / 距最近一次申请 |
   | 主体 | `id` / `cell` | 按身份证号查询 / 按手机号查询 |
   | 业务类别 | `pdl` 线上小额现金贷、`caon` 线上现金分期、`caoff` 线下现金分期、`coon` 线上消费分期、`cooff` 线下消费分期、`rel` 信用卡（类信用卡）、`af` 汽车金融、`oth` 其他 | |
   | 机构类别 | `bank` 银行（`tra` 传统银行 / `ret` 网络零售银行）、`nbank` 非银（`p2p`、`mc` 小贷、`ca` 现金类分期、`cf` 消费类分期、`com` 代偿类分期、`nsloan` 持牌网络小贷、`autofin` 持牌汽车金融、`sloan` 持牌小贷、`cons` 持牌消费金融、`finlea` 持牌融资租赁、`else`/`oth` 其他） | |
   | 时段 | `week` 周末、`night` 夜间 | |
   | 度量 | `allnum` 申请次数、`orgnum` 申请机构数、`selfnum` 在本机构申请次数、`tot_mons` 有申请记录月份数、`avg_monnum` 平均每月申请次数、`max_monnum`/`min_monnum` 最大/最小月申请次数、`max_inteday`/`min_inteday` 最大/最小申请间隔天数、`inteday` 间隔天数、`consnum` 连续申请次数、`csinteday` 连续申请持续天数 | |

   例：`als_m12_id_nbank_finlea_orgnum` = 按身份证号查询，近 12 个月在非银机构-持牌融资租赁机构申请机构数。

   > 完整的逐字段中文释义见钉钉原文 §3.2.2（约 700 行表格）。本服务**不做字段白名单、
   > 不改写字段名**：`resp_data` 整体压缩成 JSON 字符串经下游 `body.result.range`
   > 透出（与 blk/sffx 同口径），上游新增因子无需改代码即可透传。

### ★ SW0001「认证失败」的计费处理（本路由独有的一类口径）

上游把 `SW0001` 标成 **收费**，但它既不是"查得"也不是上游侧故障。难点在于：
`SW0001`（上游收费）与 `SW0002`（上游不收费）**都只能归一到 `999` 查无**，而
`billing.billNotFoundRoutes` 是「整条路由的 999 一刀切计费」的开关——一旦把 dtjd
加进去，`SW0002` 也会被计费，变成**对下游多收钱**。

**本路由的处理（产品决定）**：

- 下游一律收到 `body.code = 999` 查无（`body.msg` = "查无结果"，不泄露上游归因）；
- **我方不向下游计费**（`dtjd` 不在 `billNotFoundRoutes` 里）；
- 上游那一侧的成本由 `slog.Warn` + 审计里的 `resp_order`（上游订单号）**人工对账**。
  日志关键字：`multiloan 上游返回 SW0001 认证失败(上游文档标【收费】), 我方按查无且不计费返回, 请人工对账`。

⚠️ 对照兄弟产品：zlf 租赁分V2-D 的同一张码表里 `SW0001` 标的是**不收费**。同一供应商、
同一端点，SW0001 口径相反——这正是 `billing-scope` skill 说的「逐产品看文档，禁止复用
兄弟路由的结论」。**待上游书面确认 SW0001 的实际扣费场景与口径后回来更新本节**。

## 与本服务（dtjd 路由）的映射备忘

- 对外路由：`POST /v1/openapi/zlx/querySrmxDTJD`、`GET /v1/openapi/zlx/quotaDTJD`（x1 信封）。
- `config.yaml` → `versions.dtjd.upstreams[0]`：`kind: multiloan`、`baseURL`（上表生产 URL）、
  `institutionId`、`aesKey`、`service`/`mode`（可省用默认）、`licenseFile`/`licenseType` + `oss.*`。
- 独立成域：库 `datahub_dtjd_db`、独立 Redis 逻辑库、独立 license / 统计 / 操作日志。
- 上游 `resp_order` 是唯一上游标识：成功(001)、查无(999)、业务失败三条路径都落审计
  （`UpstreamUID` 与 `UpstreamLogID` 同填该值）。
- **调用方服务器出口 IP 需先加入上游白名单**（测试/生产均需）。非白名单来源在 TLS
  层即被断开、拿不到任何业务报文——那是环境问题，不要当协议问题去改代码。
