## 2 请求

### 2.1 / 2.2 方法与格式

`POST`；`Content-Type` 二选一：`multipart/form-data` 或
`application/x-www-form-urlencoded`。本服务取后者（与 zlf 实测通过的形态一致）。

### 2.3 请求参数（表单字段）

| 字段 | 类型 | 必传 | 含义 |
|---|---|---|---|
| `institution_id` | String | 是 | 我司给客户分配的唯一编号 |
| `biz_data` | String | 是 | 业务数据（见 §2.5），需 AES 加密（见 §2.4） |

### 2.4 加密过程

AES 分组模式 **ECB**，最后一个分组填充 **PKCS5Padding**；业务数据 JSON 化后用上游
分配的 AES 密钥加密，密文再做 **Base64** 编码放入 `biz_data`。
（上游提供的在线校验站点：<https://the-x.cn/cryptography/Aes.aspx>）

> **密钥形态必须验算**：AES 只接受 16/24/32 字节。兄弟产品 zlf 的沙箱密钥
> `Q0ymUIe1t26ZfG7s` 是 16 字节 ASCII，但不能假定本产品也是——代码里按
> 「原始字节 → hex 解码 → Base64 解码」依次试，全不合法立即报错，禁止静默降级。

### 2.5 业务数据内容（`biz_data` 明文，7 个字段**全部必传**）

| 字段 | 类型 | 必传 | 含义 |
|---|---|---|---|
| `name` | String | 是 | 姓名 |
| `ident_number` | String | 是 | 身份证号 |
| `phone` | String | 是 | 手机号 |
| `service` | String | 是 | 接口名称，默认值 `financial_rent_service` |
| `mode` | String | 是 | 接口模式，`mode_compass_black` |
| `licenseUrl` | String | 是 | 授权书 OSS 地址（需先上传到上游提供的 OSS），支持 pdf/jpg/jpeg/png/bmp；样例 `https://shouwei.oss-cn-shanghai.aliyuncs.com/approve_files/XXX.pdf` |
| `licenseType` | Integer | 是 | 文件类型，`0`: jpg/jpeg/png/bmp；`1`: pdf |

字段名逐字照抄：`ident_number` 是下划线，`licenseUrl`/`licenseType` 是小驼峰，
上游原样混用，**不许"纠正"成统一风格**。

原文示例（脱敏）：

```json
{
  "name": "xx",
  "ident_number": "xx",
  "phone": "xx",
  "service": "financial_rent_service",
  "mode": "mode_compass_black",
  "licenseUrl": "授权书oss地址",
  "licenseType": 0
}
```

> 示例给的 `licenseType` 是 `0`（图片），而我方启动时上传的固定授权书是 PDF，故配置里
> 按 `licenseType: 1` 填，**以实际上传的文件类型为准**，不照抄示例值。

`service` 与 zlf/dtjd 相同（都是 `financial_rent_service`），**只有 `mode` 不同**——
这是同端点多产品的区分位，抄错会查到另一个产品的数据。

## 3 响应

### 3.2.1 外层字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `resp_code` | String | 响应状态码（见 §4） |
| `resp_data` | String | 响应的主体数据 |
| `resp_msg` | String | 响应状态码对应的文字描述 |
| `resp_order` | String | **响应订单号**（唯一上游标识，对账用） |
| `timestamp` | String | 时间戳 |

> **文档自相矛盾**：§3.2.1 把 `resp_data` 的类型标成 `String`，而 §3.2.3 的成功示例里
> 它是一个 JSON **对象**。本服务**两种都兼容**（是 JSON 字符串时先解一层引号再压缩，
> 是对象时直接压缩），不挑一个赌。`timestamp` 同理标 String 而示例是数字，用
> `json.RawMessage` 收，不参与业务判断。

### 3.2.2 响应主体数据（`resp_data`）

固定 10 个字段，全部 String，取值 `1` = 命中 / `0` = 未命中：

| 字段 | 含义 |
|---|---|
| `black_list` | 是否命中黑名单 |
| `black_tag04` | 疑似短期频繁还款失败（标签） |
| `black_tag05` | 疑似短期频繁借贷（标签） |
| `black_tag06` | 疑似短期新机构频繁借贷（标签） |
| `black_tag07` | 疑似短期还款失败比例高（标签） |
| `black_tag08` | 疑似短期多机构逾期（标签） |
| `black_tag09` | 疑似中期频繁还款失败（标签） |
| `black_tag10` | 疑似短期新机构频繁还款失败（标签） |
| `black_tag11` | 疑似当前逾期较严重（标签） |
| `black_tag12` | 疑似高风险客户（标签） |

注意标签编号**从 04 起、无 01–03**，且不连续风险：文档只列到 12。本服务
**不做字段白名单、不改写字段名**，`resp_data` 整体压缩成 JSON 字符串经下游
`body.result.range` 透出，上游将来补 `black_tag13` 无需改代码。

> **`black_list = "0"` 不等于查无。** 上游给 `SW0000` 就说明查得到这个人的黑名单
> 评估结论，「未命中黑名单」本身就是有效结论（与 blk 黑名单因子V35 同理）。故
> `SW0000` 一律归一为 `001` 查得并计费，**不得**因为全 0 就改判 999。

### ★ 与兄弟产品 dtjd 的计费口径差异（本次接入最关键的一条）

**本文档 §4 的 `SW0001 认证失败` 标注是「不收费」**，而同供应商同端点的
**dtjd 多头借贷行为那份文档，同一个 `SW0001` 标的是「收费」**。

因此两条路由的落地**必须不同**：

| 路由 | `SW0001` 上游计费 | 本服务归一 | 理由 |
|---|---|---|---|
| dtjd 多头借贷行为 | 收费 | `999` + `slog.Warn` 人工对账 | 上游要收钱但我方不向下游收，见 dtjd 客户端头部 ★ |
| **snhmd 司南黑名单** | **不收费** | **error** | 上游不收钱，是纯粹的上游侧认证失败，按上游侧错误处理即可 |

snhmd 因此**没有** dtjd 那个「两个 999 口径相反」的难题：
`999` 只来自 `SW0002`（不收费），`billNotFoundRoutes` **不要**登记本路由。
这正是 `add-upstream` / `billing-scope` skill 反复强调的
「逐产品看文档，禁止复用兄弟路由的结论」。

## 7 授权书

**必须取得用户授权**。上游提供《最新标准布尔个人信息授权书（下游客户）V1.1》docx 模板，
需转成 pdf/图片后上传 OSS。配置项 `licenseFile` 指向该文件，`licenseType` 与文件真实
类型一致（pdf → 1）。
