## 2 请求

### 2.1 / 2.2 方法与格式

`POST`；`Content-Type` 二选一：`multipart/form-data` 或
`application/x-www-form-urlencoded`。本服务取后者（与 zlf 实测通过的形态一致）。

### 2.3 请求参数（表单字段）

| 字段 | 类型 | 必传 | 含义 |
|---|---|---|---|
| `institution_id` | String | 是 | 我司给客户分配的唯一编号 |
| `biz_data` | String | 是 | 业务数据（见 §2.5），需 AES 加密（见 §2.4）；加密是否成功可通过在线 aes 加密网站校验 |

### 2.4 加密过程

AES 分组模式 **ECB**，最后一个分组填充 **PKCS5Padding**；业务数据 JSON 化后用上游
分配的 AES 密钥加密，密文再做 **Base64** 编码放入 `biz_data`。
（上游提供的在线校验站点：<https://the-x.cn/cryptography/Aes.aspx>）

> **密钥形态必须验算**：AES 只接受 16/24/32 字节。兄弟产品 zlf 的沙箱密钥
> `Q0ymUIe1t26ZfG7s` 是 16 字节 ASCII，但**不能假定本产品也是**——代码里按
> 「原始字节 → hex 解码 → Base64 解码」依次试，全不合法立即报错，禁止静默降级。
> 本产品的 `institution_id` / `aesKey` 由上游按产品单独分配，**不要假定与
> zlf/dtjd/snhmd 共用同一把密钥**。

### 2.5 业务数据内容（`biz_data` 明文，7 个字段**全部必传**）

| 字段 | 类型 | 必传 | 含义 |
|---|---|---|---|
| `name` | String | 是 | 姓名 |
| `ident_number` | String | 是 | 身份证号 |
| `phone` | String | 是 | 手机号 |
| `service` | String | 是 | 接口名称，默认值 `financial_rent_service` |
| `mode` | String | 是 | 接口模式，`mode_many_overdue_behavior` |
| `licenseUrl` | String | 是 | 授权书 OSS 地址（需先上传到上游提供的 OSS），支持 pdf/jpg/jpeg/png/bmp；样例 `https://shouwei.oss-cn-shanghai.aliyuncs.com/approve_files/XXX.pdf` |
| `licenseType` | Integer | 是 | 文件类型，`0`: jpg/jpeg/png/bmp；`1`: pdf |

字段名**逐字照抄**：`ident_number` 是下划线、`licenseUrl` / `licenseType` 是小驼峰，
上游原样混用，不许「纠正」成统一风格。

下游入参只提供 `name` / `idCard` / `mobile` 三要素（三项均必填，网关前置拦截）；
`service` / `mode` / `licenseUrl` / `licenseType` 是我方配置侧的固定值，不来自下游。

## 3 响应

### 3.1 格式

JSON：`Accept: application/json;charset=utf-8`。

### 3.2.1 外层字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `resp_code` | String | 响应状态码 |
| `resp_data` | String | 响应的主体数据 |
| `resp_msg` | String | 响应状态码对应的文字描述 |
| `resp_order` | String | 响应订单号 |
| `timestamp` | String | 时间戳 |

> **文档自相矛盾**：`resp_data` 在字段表里标 String，§3.2.3 成功示例里却是对象；
> `timestamp` 标 String 而示例是数字。**两种形态都兼容**，不挑一个赌
> （`json.RawMessage` 延迟解析，见 `normalizeManyOverdueData`）。

> `resp_order` 是**唯一**的上游标识（既是订单号也是唯一可对账凭据）。成功 / 查无 /
> 业务失败**三条路径**都必须把它同时落进审计的 `UID` 与 `LogID`，一条都不能漏。

### 3.2.2 响应主体数据

`resp_data` 是一个**扁平大对象**，共 **357** 个字段（§3.2.2 字段表与 §3.2.3 成功示例
的键数量完全一致，已逐一核对），分四类：

- `xyp_cpl00xx`（78 个）——多头履约/逾期行为因子，如贷款总机构数、各时间窗口的
  还款成功/交易失败笔数与金额、是否逾期等；
- `xyp_t01…` / `xyp_t02…` / `xyp_t03td…` / `xyp_t04…`（266 个）——分层履约明细因子；
- `xyp_model_score_high` / `_mid` / `_low`——星耀Pro 小额网贷分V1 / 小额分期分V1 /
  中大额分期分V1，**范围 [350,950]，越大逾期率越低，未命中为 `-1`**；
- `xyp_var1` … `xyp_var10`——预留字段。

**绝大多数因子是「区间化输出」**：上游不给原值，只给档位编号，映射表见附录 A 的
「字段映射说明」。通用约定（附录 A 第一张映射表）：

| 输出值 | 含义 |
|---|---|
| `0` | `0` |
| 空 | 缺失 |
| `-1` | 负数 |

少数字段是 `1 - 逾期 / 0 - 未逾期` 的布尔语义（如 `xyp_cpl0044` 当前是否存在逾期未结清）。

> **落地口径：不做字段白名单、不改写字段名、不解释区间语义**——`resp_data` 整体压缩成
> 紧凑 JSON 字符串经 `result.range` 透出，区间含义由下游按本文档附录 A 自行解释。
> 上游将来新增因子无需改代码即可透传。

### 3.2.3 成功示例

见附录 A §3.2.3（原文逐字保留）。注意示例里绝大多数因子是空串 `""`、三个模型分是
`"-1"`——这属于「上游给了成功码 + 有效结论」，**照常计费**，不得因为值大多为空就改判
999（与 blk / snhmd 同理）。仅当 `resp_data` **整体**缺失 / `null` / 空对象 `{}` 时才
视为拿不到数据 → 上游侧错误、不计费。

## 5 授权书与 OSS

文档 §7：**必须取得用户授权**。授权书需先上传到上游提供的阿里云 OSS，再把 `licenseUrl`

`uploadAuthLicense` 把配置里的固定授权书文件（`licenseFile`）上传一次，缓存 `licenseUrl`
供该路由所有查询复用；`objectPrefix` 必须以 `approve_files/` 开头。
OSS 测试/生产凭证联系上游商务获取（文档 §6）。
