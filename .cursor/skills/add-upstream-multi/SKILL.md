# DataHub 新增多上游轮询路由

一条路由挂 N 个**可互相替代**的上游：它们提供**同一种数据**，只是供应商/价格/覆盖率
不同。调用方式是**按优先级串行、命中即停**——第一个查得数据的源就是最终结果，后面的
源一律不再调用（省钱）。**基础改动清单与 add-upstream skill 完全相同**（model/router/
config/main/mock/测试/文档 19 条照走），本文件只讲轮询特有的差异点。

> **不适用**：若一条路由的多个源提供**不同种类**的数据、可以分别命中、且要按"实际
> 查得了哪几类"组合计费（如发票数据 + 税务数据，可能只查得一半），那是另一个模型
> ——见 DataHub_SWFP 仓的 `add-upstream-multi` skill（维度寻源 + 综合源 + 缺项补齐
> + 分档计费）。**不要**把维度/组合那套复杂度搬到本模型里；本模型只有一种数据，
> 命中就是命中，不存在"查得一半"。

## 当前代码状态（动工前必读）

[internal/infrastructure/upstream/aggregate.go](internal/infrastructure/upstream/aggregate.go)
目前实现的是**并发扇出**（`sync.WaitGroup` 同时调所有子源、合并成分段 range），
**不是**本 skill 描述的串行轮询。本 skill 是目标模型，首次按它新增路由时要先把
`Aggregator` 换成串行寻源器，这部分代码尚未落地。

- **已验证的参考实现**：DataHub_SWFP 仓的
  `internal/infrastructure/upstream/sourcing.go`——把其中的维度（`DimSet`）、综合源、
  缺项补齐、分档计费全部去掉，只留「按 `(priority, 成本, 配置顺序)` 排序 + 串行遍历 +
  命中即停 + 逐源轨迹 + 总时延预算」，即为本模型。该仓已跑通全量 e2e，直接抄它的
  骨架比从零写安全。
- **不要顺手删掉 `Aggregator`**：本仓仍用它做 `len==1` 直通与未来的多源并发聚合；轮询模型落地时新增 `Sourcer` 与之并存，按路由选用。
- 落地后回来更新本节，把"尚未落地"改成实际文件与函数名。

**最小实现清单**（换 `Aggregator` → `Sourcer` 时）：

1. `Source{Name, Provider, Priority, Optional, Calls []Call}` +
   `Call{Label, CostFen, CostOn, Port}` + `NewSourcer(sources, budget)`：构造时按
   `(Priority 升 → 逻辑源总成本升 → 配置顺序)` 稳定排序，未显式给 priority 时全为 0，
   自然退化为「价格由低到高」。**即使绝大多数源只有一次调用也要保留 `Calls` 这层**
   ——需要两次调用才完整的源必须绑成一个逻辑源（铁律 2），事后再加这层要改遍所有
   调用点。
2. `Query`：串行遍历，`ok` 即 `return`；`empty`/`error` 继续下一个；每源记一条轨迹
   （`status` = `ok|empty|error|skipped` + `reason` + 上游 `code/uid/logid` + 成本 +
   耗时）；未调用的源统一补 `skipped` 行。
3. 总时延预算（`upstream.budget`，缺省 9s）：`context.WithTimeout(ctx, 剩余预算)`，
   预算耗尽不再尝试下一个源，只记 `reason`。
4. 判定：见下方判定表；全失败必须返回 `*model.UpstreamError`（`busiErr`）而非裸
   `fmt.Errorf`。
5. `Requery`：仅单源配置时直通，多源返回 `&model.RequeryResult{Reachable:false}`
   保持 PENDING 由对账兜底。
6. 单测：命中即停（低优先级源零调用）、主源查无回落到备源、全查无 999、
   部分失败但有源查得 001、全失败携带上游标识、预算耗尽跳过。

## 第 0 步补充：轮询特有的待确认项

在 add-upstream 第 0 步之外，还必须向用户确认：

1. **源清单**：N 个源各自的 endpoint/凭证/协议——是同一平台多产品码，还是完全独立的
   多家上游（各自域名协议）？
2. **优先级依据**（本模型的核心决策）：按**成本**（先便宜后贵）？按**数据质量/覆盖率**
   （先准后全）？还是有合同约定的调用配额？要拿到明确排序，不能自己猜。
3. **各源单价与计费口径**：`costFen`（分）+ 是"调用即计费"还是"仅命中计费"——不同
   上游商务条款不同，必须按源可配（`costOn: call|hit`）。
4. **各源字段能否归一到同一份下游契约**（最关键，见铁律 1）：如果各源返回的字段集
   不同，必须先定出统一的下游字段表，再逐源写映射。**这件事没确认清楚不要动笔**。
5. **"查得"的判定口径**：有些上游查无也返回 HTTP 200 + 空数组/空对象，必须问清哪个
   字段、哪个值才算真正查得——判错会让轮询在第一个源就误停，后面的源永远调不到。
6. **总时延预算**：串行最坏情况是各源耗时相加，要与下游约定的超时对齐。
7. **下游入参（铁律，同 add-upstream 的"入参与上游严格对齐"）**：多源路由的入参必须
   是**所有源都能接受**的字段集合；字段名对齐上游真实契约（上游文档示例与服务器报错
   不一致时**以服务器报错为准**），必填/选填口径与上游一致——上游必填的字段由网关
   校验器前置拦截，禁止透传给上游报错兜底；测试必须覆盖每个必填字段的"缺失拦截"。
   若各源的必填字段不同，取**并集**做前置校验（否则轮询到某个源才报错，前面的钱
   已经花了）。
8. **读完上游文档的每一页，不要只 grep 关键字段表**：PDF/接口文档常把"字段表"和
   "接入代码示例/鉴权流程/错误码附录"分成前后两部分，字段表在前几页，真正的鉴权
   协议、签名算法、错误码含义在文档中后段甚至最后。曾有案例只读了前 120 行
   字段表就动手写了 MD5 签名 + JSON body 的假协议，实际上游是 HMAC-SHA256 +
   `application/x-www-form-urlencoded` 表单——协议形态整个猜反了。**动笔前用 Read
   工具完整读完 PDF 全文**（该工具会自动分页渲染），而不是用 pdftotext/grep 抽片段。
9. **要签名算法源码，不要只凭文档描述实现**：文档只写"调用 xxxHelper.sign()"没给
   内部实现时，问用户要 SDK/demo 压缩包（关键词：demo、SDK、示例代码）。曾有案例
   `SignedRequestsHelper.java` 到手后才发现真实算法是 HMAC-SHA256（密钥为
   secretAccessKey 的 Base64 解码结果），此前假设的 MD5 完全是猜的——凭空实现的签名
   算法上生产必然 100% 验签失败。
10. **上游服务器的报错信息比文档/demo 示例更权威**：官方 demo 给的业务参数示例是
    `args={"prodCode":"...","entInfo":"统一社会信用代码"}`，签名/鉴权都通过了，但真实
    联调时上游报 `E1000 查询参数校验不通过,creditCode:为必填项`——真实字段名是
    `creditCode`。**只要签名/鉴权已经打通，服务器明确点名某个业务字段的错误信息，
    就以此为准改字段名**，不要继续信任文档示例。

## 铁律（违反任何一条即返工）

1. **各源必须归一到同一份下游字段契约**。轮询模型下下游拿到的数据来自"哪个源命中"
   这个不确定的因素，如果各源字段集不同，**下游看到的结构会随命中源漂移**——这是本
   模型唯一的架构性风险，也是与并发聚合模型最大的不同（聚合是按源分段透出，天然
   不需要归一）。做法：
   - 定一份**统一的下游字段表**（有客户契约文档就以它为准，没有就与用户定一份）；
   - **`result.range` 不按源分段**：命中即停下只有一个源出数据，range 应与单源路由
     **完全同形**（下游无从察觉背后有几个源，源可随时增删换）。分段结构（`{"源N":…}`）
     是并发聚合模型的产物，本模型不要沿用；下游若确实要求知道数据来源，也只给约定的
     脱敏编号，不给厂商/产品码。
   - 每个源写一层映射：**严格白名单**（只输出契约定义的字段，上游多余字段一律剔除）、
     契约定义而上游缺失的字段**输出空串**；
   - **语义映射要逐字段核对**：不同源的同名义字段口径可能不同（含税/不含税、统计
     范围、日期格式、精度），照样映射进同一契约字段名，但把口径差异**先列成差异表
     和用户确认**，不许静默映射；差异要写进对外手册（按"数据源"标注，不暴露厂商）。
   - 映射层必须带单测：白名单剔除、缺失补空、每个源各一份样本 → 同一份输出结构。
   - **归一不了就不要做轮询**：若各源数据结构差异大到无法归一（字段语义根本不对应），
     应回头与用户确认是不是该做成"按源分段透出"的聚合模型，而不是硬轮询。
2. **一个源需要多次调用才完整时，必须绑成一个逻辑源**。若某个源要调两次接口才拿到
   完整数据（如上游把一份数据拆成 part1/part2 两个产品码），这两次调用必须同属一个
   逻辑源、一起发出、一起判定——否则"命中即停"会在 part1 命中后停下，**下游拿到的
   字段是残缺的**。逻辑源内的多次调用可以并发（同源同价，没有短路空间可省）。
   逻辑源名同时是"本次已调用过"的去重键。
3. **命中即停，且一次请求内绝不重复调用同一个源**。重复调用等于重复付费且拿不到新
   数据。轨迹里要能看出"哪些源被短路掉了、为什么"（`status=skipped` + `reason`）——
   客户质疑"为什么没查到"时这是唯一能自证的材料，也是成本对账的依据。
4. **总时延预算是硬闸门**。串行最坏情况是各源耗时相加，预算用尽后不再尝试下一个源。
   **禁止**为了多试一个源而放宽预算把下游拖到超时——省钱的前提是不违约。
5. **失败也要可追查**（同 add-upstream 铁律，轮询下更容易踩）：子源"已应答但业务
   失败"时上游订单号/请求号在 `*model.UpstreamError` 里（此时 `res` 为 nil，只从
   `res` 取会全空），必须 `errors.As` 捞出 `Code/UID/LogID/Msg`。台账/审计的
   `上游uid`/`上游logId` 取**代表源**的值：优先命中源，其次第一个带上游标识的源——
   有上游应答时这两列永不为空。全部源失败时返回 `busiErr(...)` 而非裸 `fmt.Errorf`。
6. **一源一文档，逐个对齐**。多源常来自不同厂商、不同协议、不同文档，**禁止**把已
   实现源的协议、凭证口径、加密方式套用到新源上：
   - 每个源都单独按 add-upstream skill 的「每个源必须与该源自己的文档逐字一致」铁律
     走一遍完整核对（接口清单/字段名大小写/文档自相矛盾时两种都兼容/凭证编码形态要
     数长度验算/结果码全覆盖/生产测试两套地址）；
   - 第 0 步**逐个源**要文档，缺哪个源的文档就问用户要，不许凭"其它源是这么做的"推断；
   - 每个源客户端的文件头注释写清**它依据的是哪一份文档**；映射表标注依据**哪份文档
     的哪一节**；
   - **交付前逐源过四层**：源N 的文档 → 源N 的 client → 源N 在真实配置里的
     `upstreams` 条目（凭证是真值而非 `REPLACE_WITH_…`）→ 源N 在归一映射层里的映射。
     四层齐了才算完，缺一层就是线上"调不通"。
   - **警惕"看似冗余的双重编码"**：部分上游 demo 会对同一字段做两次 URLEncode（业务
     参数 JSON 手动 encode 一次 + 表单库整体再 encode 一次）——这不是 bug，是协议约定
     的一部分，必须原样复刻，不要"优化掉"。反过来也要小心不要叠加：若某个值（如签名
     结果）已内置一次编码，就不能再手动编码。逐字段数清楚"经过了几次 encode"再落地。

## 判定表（写代码前和用户对一遍）

| 轮询结果 | body.code | 计费 | 台账 |
|---|---|---|---|
| 某个源查得（后续源 `skipped`） | `001` | **计费** | BILLED |
| 全部源查无（无失败） | `999` | 不计费 | BILLED |
| 无源查得 + ≥1 源失败 | `002` 未取得数据且部分数据源异常 | 不计费 | BILLED |
| 全部源失败 | 返回 error → `505062` | 不计费 | PENDING→复查/对账 |

- 「查得」= 该源给出了数据；「查无」= 该源给出确定结论但无数据；「失败」= 网络/系统/
  账户错误。
- **命中即停意味着不存在"部分数据"**：只要有源查得就是完整结果（`001`、计费），
  哪怕前面几个源失败过。`002` 只表示"一个数据都没拿到，且有源异常"。
- 单一数据类型下**不需要分档计费**：查得就按该路由单价计一次
  [billing.go](internal/domain/billing/billing.go) 的 `returnedCodes={001}` 已满足，
  **零改动**。（分档计费是 DataHub_SWFP 的模型，本模型不要引入。）

## 与单上游的差异点

1. **billing / mapping 已就位，无需改动**：
   [billing.go](internal/domain/billing/billing.go) 的 `DefaultTable()` 里
   `resolvedCodes` 已含 `"002"`（确定结论、BILLED、不计成功查得数），
   [mapping.go](internal/domain/mapping/mapping.go) 的 `NotFound()` 已在
   `r.Range != ""` 时透出 `result.range`。单上游路由永不产生 002，无影响。

2. **串行寻源器**（替换 `Aggregator`，见上「当前代码状态」的最小实现清单）：
   对 orchestrator 仍是一个 `port.UpstreamPort`，完全透明。**新增轮询上游时通常只需
   写单源 client**（归一为 `001` 查得 / `999` 查无 / `*model.UpstreamError` 失败），
   排序/串行/判定/轨迹交给寻源器。
   - **协议适配点集中在一个函数**：上游文档若缺鉴权/信封细节，按最简假设实现并注释
     `// TODO 联调适配`，联调时只改这一个函数。
   - `Requery` 未联调前照旧返回 `&model.RequeryResult{Reachable:false}`。

3. **config**（[cmd/relay/config.go](cmd/relay/config.go)）：`upstreamConfig` /
   `fileUpstream` 各加轮询属性——`priority`（越小越先，缺省 0）、`costFen`（该次调用
   上游单价，分）、`costOn`（`hit` 缺省 / `call`）；`label`（轨迹与日志里的源名）与
   `optional`（`scope=basic` 跳过可选源）已存在。同一逻辑源的多次互补调用另加
   `source`（逻辑源名）。另需新增顶层 `upstream.budget`（总时延预算，缺省 9s）。
   config 一律用 `versions.<route>.upstreams` 列表：每个源一个列表项、**自带完整
   凭证**（即使同平台同凭证也各写一份，保持源完全独立、可分别替换/下线）。不要把多源
   凭证拍平成一堆无前缀字段，也不要用已废弃的单块 `upstream:` + `products` 数组。
   *踩过的坑*：多源代码写完了但生产配置还停在 `products:` 写法上（早已不被
   `loadConfig` 解析），结果只装配出一个 product 为空的子源，线上表现就是"调不通"。

4. **参数校验器按路由替换**（入参非个人三要素时才需要）：
   - [model.go](internal/domain/model/model.go)：`QueryCommand`/`UpstreamRequest` 加
     新入参字段——handler 的 json 解析与签名 bodyParams 都是泛化的，零改动；
   - [parse.go](internal/domain/parse/parse.go)：新增 `Parse<Xxx>` 校验器（必填口径
     取各源必填字段的**并集**，见第 0 步第 7 条）；
   - [main.go](cmd/relay/main.go) `buildRouteStack`：按 upstream kind
     `orch.WithParser(parse.ParseXxx)`；
   - 审计的 Name/IDCard/Mobile 掩码字段对此类路由留空即可，不要把新入参塞进去。

5. **mock 一个进程模拟全部源**（`scripts/mock_<kind>.go`）：单端口实现全部源，用
   **特殊入参值**驱动场景（照惯例用手机号/编码值触发）：
   - 正常值 → 第一优先级源即查得（用于断言**后续源零调用**）；
   - 「主源查无值」→ 高优先级源查无、低优先级源查得（断言**回落**生效）；
   - 「全查无值」→ 全部源查无（999）；
   - 「主源失败值」→ 高优先级源失败、低优先级源查得（断言失败也会回落，且最终 001）；
   - 坏鉴权 → 全部源失败（505062）。
   mock 必须能**分别统计每个源被调用了几次**（如各源一个计数器 + 一个查询端点），
   否则"命中即停"根本无法断言——这是本模型测试与聚合模型最大的差别。

6. **测试用例多四个场景**：照抄单上游用例集（错签/未知 appKey/缺 appKey/参数非法）
   之外，必须覆盖：
   - **命中即停**：正常值查询后断言低优先级源**调用次数为 0**（不能只断言 body.code）；
   - **回落**：主源查无/失败时断言备源被调用且最终 `001`；
   - **全查无 → 999**；
   - **全失败 → 505062**（且审计的上游 code/uid/logId 三列非空）。
   入参字段按本路由实际入参写；appKey 用 `harness.AppKeyFor(version)`。

## 验证补充

按 add-upstream 验证三步走；memory 冒烟必须打满五个场景：命中即停（含备源零调用）、
回落命中、全查无 999、无数据+部分失败 002、全失败 505062。

## 上线注意补充

- 对外文档（api-doc skill）里 `002` 要有独立行：含义（**未取得数据**且部分数据源
  异常）、计费=否。**不要**向下游暴露"有几个源、命中了哪个源、源的优先级"——轮询是
  我方内部的成本策略，手册里只描述"本服务返回该数据"。
- **"调用上游次数"（totalCalls）口径 = 下游一次查询计 1 次**，不按源乘 N（哪怕这次
  串行调了 3 个源）。逐源明细与成本另行记录，不要混进配额计数。
- 成本对账：若 `costFen` 全为 0，成本统计恒为 0（无意义）。上线前按上游结算价填入；
  若需要逐源成本落库/后台下钻，参考 DataHub_SWFP 的 `upstream_call` 表设计，
  **不要**把 N 个源的上游标识归并成一对写进台账（那样只留 1 个、其余丢弃，无法逐笔
  向各家上游核对）。
- **上游连不通先分清是谁的问题**：本机直连被秒断（`curl: (52) Empty reply from
  server`）通常是**上游按源 IP 白名单**，不是代码错——把部署机出口 IP 报给上游加白
  并从该机复测，别把白名单问题当协议问题去改代码。
